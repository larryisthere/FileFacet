## OQ-001：独立分发版本的自动更新方案

- 状态：待确认
- 提出日期：2026-07-15
- 影响范围：产品分发、更新交互、网络与隐私边界、签名和发布流程

### 背景

用户希望应用提供接近 HandBrake 的自动更新提醒：发现新版本后展示当前版本、可用版本和发布说明，并允许用户跳过该版本、稍后提醒或立即安装更新。

当前工程启用了 App Sandbox 和 Hardened Runtime，默认不发起网络请求。工程尚未接入更新框架，也尚未确定正式分发渠道。引入第三方运行时依赖前需要记录架构决策。

### 待确认问题

1. 正式版本采用 Mac App Store 分发、独立分发，或同时提供两种渠道？
2. 独立分发版本是否采用 Sparkle 2 及其标准更新窗口？
3. 更新包、`appcast.xml` 和发布说明由 GitHub Releases、独立静态站点或其他服务托管？
4. 应用何时检查更新：仅由用户手动触发、启动后定期检查，或同时支持两种方式？
5. 首次启用定期检查时，是否由用户明确选择？检查周期采用多长时间？
6. 下载和安装是否始终由用户在更新窗口中确认？是否允许后台预下载？
7. 发布说明使用内嵌 HTML、远程页面或纯文本？是否需要中英文版本？
8. 跳过版本、稍后提醒、下载失败、签名验证失败和安装失败分别采用什么反馈与恢复方式？

### 当前建议方案

若正式版本采用独立分发，建议使用 Sparkle 2：

- 通过 Swift Package Manager 引入 Sparkle。
- 使用 Sparkle 标准更新窗口，提供“跳过此版本”“稍后提醒”和“安装更新”。
- 在应用菜单中提供“检查更新…”。
- 支持周期性版本检查；发现新版本后再显示更新窗口。
- 通过 HTTPS 提供 `appcast.xml`、发布说明和更新包。
- 更新包使用 Developer ID Application 签名，启用 Hardened Runtime，并完成 Apple Notarization 与 stapling。
- 使用 Sparkle EdDSA 签名验证更新来源；私钥仅保存在发布机器或 CI Secret 中。
- 更新检查只传输完成版本判断所需的请求，不上传视频路径、文件名、标签内容、Bookmark 数据或资料库内容。
- Mac App Store 构建交由 App Store 更新机制处理，并在对应构建中关闭 Sparkle 更新入口。

### 预期用户流程

1. 用户通过“检查更新…”主动检查，或应用按照已确认的策略定期检查。
2. 没有新版本时，主动检查会明确提示当前已是最新版本；定期检查保持安静。
3. 发现新版本时，更新窗口展示应用图标、当前版本、可用版本和发布说明。
4. 用户可以跳过当前版本、稍后提醒或开始安装。
5. 用户选择安装后，应用展示下载和验证进度。
6. 下载及签名验证成功后，Sparkle 安装新版本并重新启动应用。
7. 下载、验证或安装失败时，用户看到明确原因，并可重试或退出更新流程。

### 工程与发布约束

- App Sandbox 需要允许更新检查所需的客户端网络连接。
- Sparkle 的更新组件、XPC 服务和主应用必须使用一致且有效的发行签名。
- 正式更新只能从已签名并完成公证的发行包生成。
- `CFBundleShortVersionString` 用于展示版本，`CFBundleVersion` 用于构建版本与升级判断，两者需要纳入发布流程。
- `appcast.xml` 更新应在更新包完成上传和可用性验证后发布，避免用户收到无法下载的版本。
- 更新机制引入网络请求和第三方运行时依赖，需要分别更新隐私边界与架构决策记录。

### 进入实现前的确认条件

- 确认正式分发渠道。
- 确认 Sparkle 2 作为独立分发更新框架。
- 确认版本检查、下载和安装策略。
- 确认更新托管位置与 Release Notes 格式。
- 完成包含主要流程、关键状态和失败反馈的可操作 HTML 原型，并由用户确认交互与 UI 方向。

### 关闭条件

完成上述确认后：

1. 将用户侧更新行为写入产品需求。
2. 新增自动更新与独立分发架构决策记录。
3. 将本问题状态更新为“已决定”，并链接对应文档。

## OQ-002：中英双语与本地化基础

- 状态：已决定并完成实施（2026-07-30，已通过用户验收）
- 提出日期：2026-07-19
- 影响范围：应用界面、动态文案、辅助功能、系统格式、公开文档、发布说明和 App Store 元数据

### 背景

FileFacet 已在 GitHub 开源，英文界面和英文公开资料是触达更多用户、接收 issue 与贡献、发布版本和后续进入 App Store 的基础能力。当前产品和界面仍在持续变化，同时维护更多语言会持续增加翻译与验收成本。

实施前，Xcode 工程以英文作为开发语言，但只声明了 `en` 和 `Base`，尚未提供 String Catalog、英文界面文案或简体中文本地化资源。应用中的菜单、工具栏、导入反馈、标签管理、空状态、错误、设置、Tooltip 和 Accessibility Label 仍有大量中文硬编码。部分动态反馈依赖中文语序和手动片段拼接，侧边栏还有通过中文展示标题判断节点类型的实现。

### 落地文档

- [中英双语与本地化 Requirements](localization-requirements.md)
- [中英双语与本地化 Design](localization-design.md)
- [中英双语与本地化 Tasks](localization-tasks.md)
- [中英双语视觉与状态原型](../prototypes/localization/index.html)

### 已确认的产品方向

- 当前版本建立完整的国际化基础，只发布英文 `en` 和简体中文 `zh-Hans`。
- 英文作为开发语言和默认回退语言。
- 系统首选语言匹配简体中文时显示简体中文，其余语言回退英文。
- 应用跟随系统语言，不提供应用内语言切换入口。用户仍可使用 macOS 提供的单 App 语言设置。
- 日语、韩语、繁体中文、德语、法语等语言在出现真实用户需求或上架要求后单独评估。
- 繁体中文需要独立处理术语、语气和 macOS 系统用词，不使用简体转繁体作为正式本地化结果。
- 当前阶段不接入翻译平台，不批量发布机器翻译语言。

### 用户数据与本地化边界

- 标签名称、资料库名称、文件名、文件路径及其他用户输入保持原值，不参与翻译。
- 用户数据只能作为本地化字符串参数传入，不能作为本地化 key。
- 标签按名称排序继续依据当前系统 Locale 处理比较，不改变或翻译标签内容。
- 日期、数字和文件大小使用系统 Locale 对应的格式。
- 媒体时长可以继续采用通用的 `mm:ss` 或 `hh:mm:ss` 表示。
- 产品名称 `FileFacet`、内部 Xcode 工程名 `VideoTagManager` 和现有 Bundle ID 保持稳定。

### 本地化资源与代码约束

- 使用 `Resources/Localizable.xcstrings` 作为应用文案的统一资源，包含英文和简体中文。
- AppKit 文案统一通过 `String(localized:)` 或项目确认的等价封装读取，使用语义化 key，例如 `library.allVideos`。
- SwiftUI 可见文案也进入同一 String Catalog，避免依赖散落在视图中的中文文本。
- 菜单、工具栏、按钮、系统面板、错误信息、空状态、设置项、Tooltip、Accessibility Label 和图标的 accessibility description 全部进入本地化资源。
- 包含数量的文案使用 String Catalog 的复数变化，英文至少覆盖 `one` 和 `other`。
- 动态文案按完整含义本地化，不拼接依赖特定语言语序的句子、名词、标点或状态片段。
- 展示文字不能承担业务身份。侧边栏分组等逻辑使用稳定枚举或节点 ID。
- 数据库错误保留稳定 case，用户看到的错误在界面边界转换为完整的本地化文案；未被消费的 operation 参数不进入错误模型。
- 文本按钮依赖 intrinsic content size 或合理的最小宽度，不使用只适配中文文案的固定宽度。
- 表单标题、工具栏、设置侧栏、状态区域和空状态允许英文文案换行、扩展或合理截断。
- Xcode 工程和 `tool/generate_xcode_project.rb` 同步登记 String Catalog，保证重新生成工程后资源仍然存在于 App target。

### 公开资料与发布语言

- 仓库默认 `README.md` 以英文为主。
- 提供 `README.zh-CN.md`，两份 README 在顶部互相提供语言入口。
- issue 模板、贡献指南、安全报告入口和 GitHub Release Notes 优先使用英文。
- `CHANGELOG.md` 使用英文，现有 Fastlane GitHub Release 流程继续从中提取英文发布说明。
- 仓库内部产品与架构文档可以继续使用中文，不纳入本轮应用本地化范围。
- App Store 上架时同时准备英文和简体中文名称、简介、描述、关键词、隐私说明和版本说明；对应元数据在上架流程中单独管理。

### 本轮实施范围

1. 新增英文与简体中文 String Catalog，并配置工程语言和英文回退。
2. 迁移所有用户可见文案、辅助功能文案和用户可见错误。
3. 重构复数、动态句式、手动列表连接和依赖展示文字的逻辑判断。
4. 检查英文长度影响到的按钮、表单、工具栏、侧栏、状态和空状态布局。
5. 更新 README、CHANGELOG 和 GitHub issue 模板等公开入口资料。
6. 将确认后的长期规则同步到当前产品需求；如实施引入新的本地化抽象或运行时依赖，再补充架构决策记录。

本需求不新增应用内交互流程，可以在确认 OQ 后直接进入实现，无需先制作 HTML 原型。

### 暂不包含

- 日语、韩语、繁体中文、德语、法语及其他新增语言。
- 应用内语言选择器及其偏好存储。
- 机器翻译批量发布。
- 第三方翻译平台、远程文案服务或新的运行时依赖。

### 验收边界

- 英文系统环境中的菜单、主窗口、导入流程、标签管理、设置、错误、空状态、Tooltip 和 Accessibility 文案均显示英文。
- 简体中文系统环境中的上述界面均显示简体中文。
- 繁体中文及其他未支持语言环境回退英文。
- 英文环境中的零个、一个和多个对象文案符合英文复数规则。
- 切换界面语言后，标签名称、资料库名称、文件名和路径保持原值。
- 日期、数字和文件大小符合当前系统 Locale。
- 英文长文案没有造成按钮截断、布局重叠或关键反馈不可见。
- VoiceOver 读出的可操作控件名称与当前界面语言一致。

工程实现完成后默认只验证 Debug 构建成功，再交由用户按上述中英双语场景验收。构建成功只确认资源和代码能够编译，不能替代语言覆盖、布局和辅助功能验收。

### 实施结果

- `Resources/Localizable.xcstrings` 已覆盖英文与简体中文，英文为开发语言和默认回退语言。
- 菜单、主窗口、导入、标签、设置、应用锁、错误、Tooltip 和辅助功能文案已迁移。
- 侧栏分组业务身份已与展示标题解耦，用户数据和持久化身份保持原值。
- Xcode 工程与 `tool/generate_xcode_project.rb` 已同步登记 String Catalog。
- 用户于 2026-07-30 完成验收，本次实现与验收记录见 [Requirements](localization-requirements.md) 和 [Tasks](localization-tasks.md)。

### 关闭条件

1. 上述范围完成实现并通过用户验收。
2. 已确认规则同步到当前产品需求和发布文档。
3. 将本问题状态更新为“已决定”，并链接对应需求或架构文档。

## OQ-003：持续访问权限失败后的恢复方式

- 状态：待决定
- 提出日期：2026-07-30
- 影响范围：视频与文件夹导入、Sandbox 持续访问授权、失败反馈和恢复操作

### 背景

当所选输入全部无法创建或解析 Security-Scoped Bookmark，或无法建立安全范围访问时，导入会停止并显示“无法获得所选内容的持续访问权限”。当前状态区域只提供关闭动作，没有明确提示用户重新选择内容并确认访问。

该行为早于 OQ-002 的本地化实施。本地化只将既有失败原因迁移到 String Catalog，没有改变恢复流程。

### 待确认问题

1. 失败状态是否只补充“重新选择视频或文件夹并确认访问”的说明，继续由用户从原导入入口重试？
2. 状态区域是否增加“重新选择”操作，直接重新打开导入面板？
3. 多个输入中仅部分授权失败时，是否需要列出失败数量并提供仅重试失败项目的入口？
4. 恢复动作是否继续使用当前 52pt 状态区域，或改用可容纳完整原因与操作的 Sheet？

### 当前约束

- 不缓存或展示完整文件路径。
- 已成功加入资料库的视频继续保留。
- 重试不得重复创建视频记录或改写用户标签。
- 恢复入口需要同时覆盖文件选择器和拖入场景。

### 关闭条件

1. 确认失败反馈的文案、操作入口和承载界面。
2. 制作覆盖全部失败与部分失败状态的 HTML 稿并通过用户确认。
3. 实现后由用户验收权限恢复路径。
